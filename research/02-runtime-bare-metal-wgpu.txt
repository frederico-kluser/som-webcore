Arquitetura de Runtime Bare-Metal em
wgpu e WGSL Puro para System One
Models (SOM)
O desenho de um motor de inferência bare-metal para System One Models (SOM) exige
abandonar a arquitetura orientada a loops autorregressivos e KV-Caches dinâmicos dos
motores de LLMs tradicionais1. Como um SOM opera exclusivamente em passada única
não-autorregressiva (Single Forward-Pass) para avaliar um contexto (State) contra múltiplas
perguntas tipadas (Choice, Score e Noul) sem gerar tokens de texto3, todo o grafo
computacional possui dimensões estáticas e conhecidas no instante do dispatch2. Esta
propriedade física permite compilar um runtime em Rust puro + wgpu + bytemuck +
Compute Shaders WGSL escritos à mão que pré-aloca 100% da memória de vídeo (VRAM)
na inicialização, elimina alocações por inferência e submete todas as 16 a 28 camadas do
modelo, cabeças de pontuação e calibração probabilística dentro de um único
wgpu::CommandEncoder e um único wgpu::ComputePass com uma única chamada
queue.submit()2.
A viabilidade física em dispositivos móveis, navegadores (Wasm32/WebGPU) e servidores
nativos (Vulkan, Metal, DirectX 12) divide o catálogo de modelos abertos em duas classes
estritas6. Modelos baseados em encoders bidirecionais compactos e arquiteturas híbridas —
especificamente Von 1.3 (wfzyx/von, 395M)5, LiquidAI d1-omni-600M (587M total, 381M no
tronco textual)8, Laya (convaiinnovations/laya, 322M–421M)12 e Kev-0.8B
(jaredpalmer/kev, 800M)10 — ocupam entre 172 MB e 426 MB quando quantizados em 4 bits
(Q4_K) ou 8 bits (Q8_0), executando em 7,4 ms a 60 ms em GPUs integradas e móveis2. Em
contrapartida, adaptações System One sobre decoders densos pesados, como Bespoke
Nimble (9B e 27B) e Kev (4B, 9B e 27B), exigem de 16 GB a 55 GB de VRAM10, sendo inviáveis
para execução in-browser ou on-device em telemóveis e computadores comuns6.
Para atingir performance no limite do silício sem dependências de frameworks de Machine
Learning, o motor deve bifurcar a sua inicialização em dois perfis de hardware detetados via
Adapter::features() e Adapter::limits()6. No Perfil 1 (Browser WebGPU / Wasm32), o limite de
maxStorageBufferBindingSize (128 MiB por defeito na especificação W3C) e o teto de 4 GiB de
memória linear do Wasm32 são contornados através de streaming direto da Origin Private File
System (OPFS) para 2 a 3 Slabs de VRAM alinhados a 256 bytes, percorrendo todas as camadas
do modelo via Dynamic Storage Buffer Offsets e acelerando produtos escalares quantizados
com dot4I8Packed e reduções em registos com subgroupAdd6. No Perfil 2 (wgpu Nativo /
wgpu-hal), o runtime ativa Features::MAPPABLE_PRIMARY_BUFFERS para zero-copy real em
arquiteturas de memória unificada (Apple Silicon, APUs AMD/Intel, SoCs Android),
Features::PUSH_CONSTANTS para injeção de metadados nos registos de comando, Bindless
Storage Arrays (Features::BUFFER_BINDING_ARRAY) sobre um único bloco monolítico de
VRAM e passthrough de shaders nativos (SPIRV_SHADER_PASSTHROUGH / MSL) para acesso

PILAR 1: Catálogo de SOMs Open-Source e Viabilidade
Física (Mobile & Desktop)
A transição de LLMs geradores de texto para System One Models substitui a decodificação
sequencial de tokens pela extração direta de distribuições de probabilidade sobre um espaço
de decisão fechado e tipado1. Enquanto o modelo proprietário de referência Jev (jev-1.14.0 da
TypeSafe AI) estabeleceu o contrato de API /v1/systemone com as primitivas Choice (1 a 255
opções), Score (2 a 10 níveis ordenados) e Noul (probabilidade binária entre 0 e 1 sem campo
de confiança separado)25, a comunidade open-source desenvolveu arquiteturas nativas que
operam em passada única5.
1. Modelos SOM Nativos Open-Source
Von (wfzyx/von — 395M Parâmetros)
O Von (congelado e arquivado na versão von-1.3.0, com pesos idênticos ao von-1.2 sob o hash
SHA 5df8185a4f2327ad0a7cd117cc4f701ac557b9ae) é um SOM puramente
não-autorregressivo construído sobre o backbone answerdotai/ModernBERT-large somado
a uma cabeça leve de pontuação denominada Option-Marker (option_marker.pt)5. Embora a
versão inicial von-1.0 fosse um classificador NLI derivado de tasksource/ModernBERT-large-nli
com 134 cabeças de classificação e temperatura escalar fixa (T = 1,0367 para Noul e T = 1,1692
para Choice)1, a arquitetura a partir do von-1.2/1.3 introduziu o mecanismo Option-Marker com
atenção invariante à ordem5.
A arquitetura interna do backbone ModernBERT-large utilizado pelo Von possui exatamente 28
camadas (num_hidden_layers = 28), dimensão oculta H = 1024 (hidden_size = 1024), 16 cabeças
de atenção (num_attention_heads = 16, dimensão por cabeça D = 64), dimensão intermediária
da FFN I = 2624 (intermediate_size = 2624, que se expande para 2 × I = 5248 na projeção de
entrada da porta GeGLU) e vocabulário BPE de V = 50.368 tokens (mask_token_id = 4 ou
50284, pad_token_id = 50283, janela máxima de contexto de 8.192 tokens)7. Todas as projeções
lineares (Wqkv, Wo na atenção; Wi, Wo na MLP) e todas as camadas LayerNorm (ε = 1e-5)
operam com bias = False (zero vetores de bias em todo o backbone)35. Crucialmente para a
implementação em WGSL, o ModernBERT aplica Pre-Norm, mas a Camada 0 omite a
normalização pré-atenção (layer_0.attn_norm = None), pois o tensor já sai normalizado de
embed_norm(tok_embeddings(ids))35. Nas camadas 1 a 27, o fluxo aplica normalização
pré-atenção seguida de conexão residual e normalização pré-MLP seguida de GeGLU e
conexão residual, finalizando no topo do encoder com final_norm(x)35. Em cada camada,
mlp.Wi projeta de 1024 para 5248 canais, dividindo o tensor em duas metades x_val e gate de

LiquidAI d1-omni-600M (587M Parâmetros Totais / 381M Tronco Textual)
Lançado em outubro de 2026 como o sucessor oficial recomendado pela equipa do Von para
novos projetos11, o LiquidAI/d1-omni-600M é um SOM multimodal de passada única com
587M parâmetros totais, subdivididos em três módulos que partilham o mesmo tronco de
decisão8. O primeiro módulo é o Tronco Compartilhado e Cabeça de Decisão
(LFM2.5-Encoder-350M + Decision Head — 381M parâmetros), baseado na arquitetura
híbrida Liquid Foundation Model 2.5 (LiquidAI/LFM2.5-350M-Base convertida em encoder
bidirecional)8. Possui 16 camadas (num_hidden_layers = 16), dimensão oculta H = 1024
(hidden_size = 1024), vocabulário de V = 65.536 tokens e janela de contexto de 16.384 tokens8.
Das 16 camadas, 10 camadas são blocos de convolução curta duplamente controlada
(LFM2ShortConv) e 6 camadas são blocos de Grouped Query Attention (LFM2Attention),
intercaladas segundo a lista full_attn_idxs do config.json40. O segundo módulo é a Torre de

Laya, Kev e Nimble (Análise de Viabilidade em Passada Única)
Entre as restantes famílias open-source do ecossistema System One, apenas o Laya e a

SOM verdadeiro de passada única disponível em três checkpoints principais: laya (Inglês, 421M

sequências curtas permanecem memory-bandwidth bound6.

Arena Allocator Estático com Dynamic Storage Offsets
Na especificação base do W3C WebGPU, o limite padrão maxStorageBufferBindingSize é de
apenas 128 MiB (134.217.728 bytes) e maxBufferSize é 256 MiB (268.435.456 bytes)6. Mesmo
solicitando os limites superiores do adaptador via requiredLimits em request_device(),
dispositivos móveis e drivers D3D12 impõem tetos rígidos por binding6. Além disso, o limite
padrão de maxStorageBuffersPerShaderStage na WebGPU é de apenas 8 buffers por estágio
de shader. Se criarmos um wgpu::BindGroup separado para cada uma das 28 camadas do
Von-1.3, teremos 28 objetos de estado de descritor validados pelo navegador a cada passo; se
tentarmos ligar o modelo inteiro num único StorageBuffer, violaremos o limite de 128 MiB (já
que o Von-1.3 ocupa 212,34 MB em Q4_K e 401,09 MB em Q8_0)6.
A solução zero-bloat consiste num Static Slab Arena Allocator com Dynamic Storage Buffer
Offsets implementado em quatro passos:
  1.  Particionamento em 2 a 3 Slabs Físicos: Dividimos os pesos das 28 camadas do
      Transformer em S blocos contíguos (wgpu::Buffer com BufferUsages::STORAGE |
      BufferUsages::COPY_DST), onde cada Slab contém um subconjunto fixo de camadas. No
      Von-1.3 em Q4_K, os 343,20M parâmetros do tronco ocupam ~184,1 MB: alocamos o
      Slab A com as camadas 0 a 13 ocupando ~92,05 MB e o Slab B com as camadas 14 a 27
      ocupando ~92,05 MB, enquanto os embeddings e a cabeça de decisão ficam no Slab 0
      Estático de ~28,2 MB6. Em Q8_0 (401,09 MB), usamos 3 Slabs de ~115 MB (camadas 0–9,
      10–19 e 20–27)16.
  2.  Alinhamento Físico Estrito a 256 Bytes: A WebGPU exige que qualquer offset dinâmico
      passado em set_bind_group seja múltiplo exato de min_storage_buffer_offset_alignment
      (256 bytes). No nosso empacotador .sombin, o bloco de pesos completo de cada
      camada l (LayerWeightBlock, contendo attn_norm, Wqkv, Wo, mlp_norm, Wi, Wo
      concatenados e alinhados internamente a 256 bytes) tem um tamanho total
      arredondado para cima ao próximo múltiplo de 256 bytes:

===== PAGE 16 =====
  3.   Um Único BindGroupLayout com has_dynamic_offset: true: Criamos o
       BindGroupLayout do Grupo 1 com BufferBindingType::Storage { read_only: true },
       has_dynamic_offset: true e min_binding_size: NonZeroU64::new(layer_stride) (ex: ~6,58
       MB por camada em Q4_K, muito abaixo do limite de 128 MiB)6. Instanciamos apenas 1
       BindGroup por Slab na inicialização (bindando a janela base 0..layer_stride do respetivo
       Slab).
  4.   Travessia de Camadas sem Troca de Descritores: Durante a gravação do
       ComputePass, para executar a camada l residente no Slab s com índice local k = l -
       l_start(s), invocamos apenas cpass.set_bind_group(1, &engine.slab_bind_groups[s], &[(k
       as u32) * (engine.layer_stride as u32)]). O navegador apenas soma o offset dinâmico ao
       ponteiro base do registo de descritor na GPU, sem qualquer alocação ou revalidação de
       tabela de recursos.
Intrinsics Nativos do Padrão WGSL (Sem Extensões Proprietárias)
Para atingir velocidade nativa dentro do browser, os nossos kernels WGSL combinam as
instruções padronizadas do W3C WebGPU para produto escalar inteiro empacotado, meia
precisão e subgrupos6.
Em primeiro lugar, ativamos a aceleração 4× INT8 via dot4I8Packed e dot4U8Packed
(requires packed_4x8_integer_dot_product;)20. Introduzida na especificação core do WGSL
(Chrome 123+, tint:1497), a diretiva requires packed_4x8_integer_dot_product; expõe as
instruções de hardware DP4a (dot4I8Packed(a: u32, b: u32) -> i32 e dot4U8Packed(a: u32, b:
u32) -> u32), além das funções auxiliares de empacotamento pack4xI8, pack4xI8Clamp e
unpack4xI820. Nos nossos kernels Q8_0 e Q4_K, quantizamos dinamicamente o bloco de
ativação de entrada x em blocos de 32 valores para int8 empacotados em 8 palavras u32
(usando pack4xI8Clamp) na memória partilhada var<workgroup>, mantendo uma escala f32
por bloco20. Para pesos Q8_0, cada bloco de 32 pesos já reside na VRAM como 8 palavras u32:
o loop interno executa 8 chamadas acc_i32 += dot4I8Packed(act_u32[j], weight_u32[j]); e
acumula no registo f32 multiplicando por scale_act * scale_weight20. Para pesos Q4_K,
extraímos os nibbles inferiores e superiores de 4 bits usando máscaras bit-a-bit ((w_packed &
0x0F0F0F0Fu) e ((w_packed >> 4u) & 0x0F0F0F0Fu)) e passamos diretamente ao
dot4I8Packed / dot4U8Packed sem nunca desempacotar para f32 na memória20.
Em segundo lugar, combinamos enable f16; e enable subgroups;6. O uso de enable f16; reduz
pela metade o consumo de registos (VGPRs) e de memória partilhada (var<workgroup>) para
matrizes de atenção, enquanto enable subgroups; (Chrome 134+) disponibiliza subgroupAdd,
subgroupMax, subgroupBroadcastFirst e subgroupShuffleXor, gerando ganhos medidos de
2,3× a 2,9× em multiplicações matriz-vetor e reduções sobre implementações sem
subgrupos6. Com subgroupAdd e subgroupMax, o cálculo da média e variância no
LayerNorm/RMSNorm e o máximo e soma no Softmax ocorrem nos registos da wavefront/warp
(32 ou 64 threads), exigindo apenas uma escrita por subgrupo na memória partilhada para

===== PAGE 17 =====
reduzir entre subgrupos.
Na escrita destes shaders, é crítico contornar três erratas reais de hardware e compilador
documentadas em produção:
  ●   Bug de Driver AMD RDNA1/D3D12 em subgroupMax(vec4<f16>) (Issue #34078): Em
      GPUs AMD Radeon (RDNA1/Navi 10 sobre D3D12), chamar subgroupMax(abs(v)) onde v é
      um vetor vec4<f16> ou vec2<f16> corrompe metade das escalas de quantização
      (reduzindo apenas as lanes pares do subgrupo e gerando 29% de erro de
      dequantização)65. Nos nossos shaders WGSL, nunca invocamos subgroupMax ou
      subgroupAdd sobre tipos vetoriais vec4<f16>. Reduzimos primeiro os 4 componentes
      dentro da própria thread (in-lane: let local_max_f16 = max(max(abs(v.x), abs(v.y)),
      max(abs(v.z), abs(v.w)));) e convertemos para escalar f32 antes da operação cruzada de
      subgrupo (let block_max_f32 = subgroupMax(f32(local_max_f16));), reduzindo o erro de
      dequantização para 0 blocos errados65.
  ●   Bug de -INF em simd_max(half) em GPUs AMD sobre Metal (Issue #19563): Ao testar
      máscaras de atenção contendo -∞ em f16 (-65504.0h / 0xFC00), simd_max(half) /
      subgroupMax em f16 retorna valores incorretos em arquiteturas RDNA sob Metal67. A
      redução do máximo do Softmax na FlashAttention deve sempre converter o acumulador
      de score para f32 antes de chamar subgroupMax(score_f32)67.
  ●   Divergência da Diretiva enable subgroups; entre Naga Nativo e Dawn/Firefox
      (Issues #5555 e #8202): Enquanto os browsers baseados em Chromium (Dawn) e
      Firefox WebGPU exigem enable subgroups; no topo do ficheiro .wgsl, o parser naga
      usado pelo wgpu nativo rejeita a declaração enable subgroups; (exigindo omitir a linha no
      shader WGSL mesmo quando Features::SUBGROUP está ativo no wgpu nativo)68. O
      nosso carregador de shaders em Rust resolve isto removendo ou mantendo a linha
      enable subgroups; em tempo de carregamento consoante cfg!(target_arch =
      "wasm32")68.
Streaming Direto para VRAM no Wasm32 (Contornando as Paredes de 2 GB e 4
GB)
No navegador, o motor enfrenta duas barreiras severas de memória da CPU: o Chrome limita
qualquer alocação de ArrayBuffer em JavaScript a 0x7fe00000 (~2 GiB), fazendo com que
fetch().arrayBuffer() falhe em ficheiros grandes, e o WebAssembly 1.0 (wasm32) utiliza
ponteiros de 32 bits, impondo um teto rígido de 4 GiB de memória linear para todo o módulo
Wasm6. Se carregarmos um ficheiro de pesos na RAM do Wasm antes de o copiar para a GPU,
duplicamos o consumo de memória da aba e causamos crash em dispositivos móveis (cujo
orçamento total por aba é de ~2 GB)6.
Para obter Zero-RAM-Spike no Wasm32, o nosso carregador implementa Direct-to-VRAM
Streaming via OPFS em quatro passos6:
  1.   Ingestão em Chunks para OPFS: Na primeira execução, o ficheiro .sombin é
       descarregado via ReadableStream (response.body.getReader()) em fragmentos (chunks)
       de 8 MiB e gravado diretamente na Origin Private File System (OPFS) através de
       FileSystemSyncAccessHandle.write() num Web Worker (que é 2× a 4× mais rápido em
       leituras frias que o IndexedDB e evita a penalidade de inflação de quota de 7 MB por

===== PAGE 18 =====
       resposta opaca da Cache API)6.
  2.   Alocação de Slabs Desmapeados na GPU: Durante a inicialização do SomEngine no
       Wasm32, alocamos os Slabs wgpu::Buffer vazios na VRAM com BufferUsages::STORAGE |
       BufferUsages::COPY_DST e mapped_at_creation: false6.
  3.   Upload por Janela Deslizante de 8 MiB: Mantemos um único buffer de staging
       reutilizável de 8 MiB na heap linear do Wasm32, lemos o ficheiro .sombin da OPFS em
       janelas sequenciais de 8 MiB para esse buffer reutilizável e invocamos imediatamente
       queue.write_buffer(&slab_buffer, slab_offset, &chunk_slice)6.
  4.   Orquestração Leve no Wasm: Dessa forma, os pesos de 200 MB a 800 MB transitam
       diretamente do disco (OPFS) para os buffers da GPU, enquanto o módulo Wasm32 retém
       apenas handles leves (~150 bytes por buffer) e mantém o consumo de memória linear
       abaixo de 16 MiB durante todo o ciclo de vida da aplicação6.
2. PERFIL 2: SEM LIMITES DO BROWSER (wgpu Nativo em Vulkan,
Metal e DirectX 12)
Quando o motor executa nativamente em desktops, servidores ou dispositivos móveis (via

Zero-Copy Real em Memória Unificada (UMA) via
Features::MAPPABLE_PRIMARY_BUFFERS e wgpu-hal
Em arquiteturas de Memória Unificada (UMA) — Apple Silicon (M1 a M5), APUs AMD Ryzen AI,
Intel Core Ultra e SoCs móveis Qualcomm Snapdragon / MediaTek Dimensity — a CPU e a GPU
partilham os mesmos bancos físicos de DRAM6. Na WebGPU padrão, um buffer com
BufferUsages::STORAGE não pode ter BufferUsages::MAP_READ ou MAP_WRITE, obrigando o
motor a alocar buffers de staging redundantes e emitir comandos de cópia DMA
(encoder.copy_buffer_to_buffer())19.
No Perfil 2, verificamos se o dispositivo possui memória unificada
(adapter.get_info().device_type == DeviceType::IntegratedGpu ou backend Metal em
aarch64-apple-darwin/ios) e ativamos wgpu::Features::MAPPABLE_PRIMARY_BUFFERS19.
Para o ficheiro de pesos .sombin, fazemos mmap alinhado a páginas do sistema operativo e
usamos wgpu-hal (como newBufferWithBytesNoCopy com MTLResourceStorageModeShared
no Metal ou VK_EXT_external_memory_host no Vulkan) para expor o ponteiro virtual do mmap
diretamente à GPU sem cópia de inicialização67. Para a entrada de tokens e leitura de decisões,
alocamos o InputTokenBuffer com BufferUsages::STORAGE | BufferUsages::MAP_WRITE e o
DecisionOutputBuffer (64–256 bytes) com BufferUsages::STORAGE |
BufferUsages::MAP_READ19. A CPU escreve os IDs dos tokens e metadados diretamente no
ponteiro mapeado do InputTokenBuffer, submete o CommandEncoder com zero chamadas
copy_buffer_to_buffer e, após a conclusão da fila (device.poll(Maintain::Wait)), lê o
DecisionPacket diretamente do ponteiro físico partilhado da GPU19. (Nota de segurança: em
GPUs dedicadas PCIe onde device_type == DiscreteGpu, MAPPABLE_PRIMARY_BUFFERS é
desativado nos buffers de armazenamento principais para não degradar severamente a
performance forçando leituras da GPU através do barramento PCIe19).

PILAR 3: Otimizações Extremas que a Comunidade
Ignorou (Foco Exclusivo em SOM)
Grande parte dos projetos open-source atuais tenta servir SOMs reaproveitando motores
desenhados para LLMs autorregressivos (como vLLM, SGLang ou llama.cpp em modo
servidor)8. Isso introduz um desperdício severo: alocadores de PagedAttention para
KV-Caches que nunca crescem, samplers de vocabulário e sincronizações CPU↔GPU a cada
camada. Num motor construído especificamente para a física não-autorregressiva de um
SOM, implementamos quatro otimizações estruturais.























1. Single-Command-Encoder Full-Forward Execution (Zero Overhead
de CPU)
Em qualquer runtime de LLM, a CPU precisa intervir a cada token gerado para atualizar
ponteiros do KV-Cache, verificar critérios de paragem (EOS) e agendar a próxima iteração.

===== PAGE 21 =====
Num SOM, o número de passos é exatamente 1 e todas as dimensões (comprimento total da
sequência N, comprimento do estado state_len e número de opções K) são fixas desde o
microssegundo zero da requisição1.
Além disso, na especificação WebGPU e no wgpu, não é necessário encerrar um
ComputePass entre dispatches de compute shaders que leem e escrevem nos mesmos
buffers de armazenamento (StorageBuffers). Os drivers Vulkan, Metal, D3D12 e
Dawn/WebGPU inserem automaticamente barreiras de memória de pipeline entre chamadas
cpass.dispatch_workgroups() consecutivas dentro do mesmo ComputePass sempre que um
buffer transita de escrita para leitura.
Portanto, o nosso motor grava todas as 28 camadas do Encoder + Cabeça
OptionMarkerScorer + Calibração de Temperatura dentro de um único
wgpu::CommandEncoder e um único wgpu::ComputePass [o README adota 3 submissões; ver README §3.5], usando apenas dois buffers de
ativação em esquema Ping-Pong (act_buf_a e act_buf_b, cada um de tamanho N_max * H * 4
bytes = 8192 × 1024 × 4 = 32 MiB, mais um buffer de espaço de trabalho QKV de 8192 × 3072 × 2
= 48 MiB em f16)35:

2. Unpadded Sequence Packing + Block-Diagonal FlashAttention-2 em
WGSL

simultaneamente o isolamento de máscara em bloco diagonal e o reset de posições do RoPE

    // 2. Thread 0 executa LogSumExp, Entropia de Shannon e Calibração em f32 estrito
    if (tid == 0u) {
        var max_z: f32 = -3.402823e+38;
        for (var m: u32 = 0u; m < K; m = m + 1u) {
            max_z = max(max_z, smem_logits[m]);
        }

        var sum_exp_raw: f32 = 0.0;
        for (var m: u32 = 0u; m < K; m = m + 1u) {
            let e = exp(smem_logits[m] - max_z);
            smem_probs_raw[m] = e;
            sum_exp_raw += e;
        }

        var entropy: f32 = 0.0;
        for (var m: u32 = 0u; m < K; m = m + 1u) {
            let p_raw = smem_probs_raw[m] / sum_exp_raw;
            smem_probs_raw[m] = p_raw;

===== PAGE 43 =====
            entropy -= p_raw * log(max(p_raw, 1e-12));
        }
        let h_norm = select(0.0, entropy / log(f32(K)), K > 1u);

        // Equação exata do marker_calibration.json (Von 1.3):
        let log10_state = log(max(f32(globals.state_len), 1.0)) / 2.302585093;
        let t_raw = globals.calib_bias
                  + globals.calib_w_h * h_norm
                  + globals.calib_w_len * (log10_state * 0.25)
                  + globals.calib_w_k * (f32(K) * 0.125);
        let temp = clamp(t_raw, 0.3, 12.0);

        var sum_exp_cal: f32 = 0.0;
        for (var m: u32 = 0u; m < K; m = m + 1u) {
            let e_cal = exp((smem_logits[m] - max_z) / temp);
            smem_logits[m] = e_cal;
            sum_exp_cal += e_cal;
        }

        var best_idx: u32 = 0u;
        var p1: f32 = -1.0;
        var p2: f32 = -1.0;
        var exp_score: f32 = 0.0;

        for (var m: u32 = 0u; m < K; m = m + 1u) {
            let p_cal = smem_logits[m] / sum_exp_cal;
            if (m < 8u) { decision_out.top8_probs[m] = p_cal; }
            exp_score += f32(m) * p_cal;
            if (p_cal > p1) {
                p2 = p1;
                p1 = p_cal;
                best_idx = m;
            } else if (p_cal > p2) {
                p2 = p_cal;
            }
        }

        let p_yes = select(0.0, decision_out.top8_probs[0], K >= 1u);
        var noul_out = p_yes;
        if (globals.noul_band_mode == 1u) {
            noul_out = select(
                0.2 - 0.1 * (0.5 - p_yes),
                0.8 + 0.1 * (p_yes - 0.5),

===== PAGE 44 =====
                     p_yes >= 0.5
                 );
             }

             decision_out.winning_option = best_idx;
             decision_out.num_options = K;
             decision_out.confidence = max(p1 - max(p2, 0.0), 0.0);
             decision_out.calibrated_temperature = temp;
             decision_out.noul_probability = noul_out;
             decision_out.expected_score = exp_score;
             decision_out.normalized_entropy = h_norm;
             decision_out.top1_prob = p1;
         }
     }

Com esta arquitetura de 6 shaders e o formato .sombin, o binário compilado em Rust puro
mantém-se enxuto, carrega diretamente via OPFS (no browser) ou mmap (no nativo) e executa
decisões estruturadas completas (Choice, Score e Noul) numa única submissão de comando à
GPU2.
